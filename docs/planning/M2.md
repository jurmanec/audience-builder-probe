# M2 roadmap

M2 is the plan-and-revise graph, then a grounded brief. The template path stays as it is. The one-shot path, the scored comparison, and the public README stay in M3.

The graph receives an objective string. It plans a predicate, counts it with the existing tools, and revises. It returns a draft audience or nothing. It does not read `eval/gold.json`, and it does not import the template intents. The eval harness may read the gold file and may set `status` to `approved` before the brief step.

## 1. Thin model interface

One planner function accepts the objective, the usable attribute names, and any prior attempt. It returns a predicate in the shared schema. The graph sets `estimated_size` from `count_audience` and sets `status` to `draft`.

The default provider is xAI behind that function. The model id can still change until the first live call. Tests pass a scripted planner, so the milestone does not require a network call. Bedrock stays a later swap.

## 2. Plan, count, and revise

Build the loop in LangGraph. The nodes call the existing Python tools. `list_usable_attributes` runs once per run. `count_audience` runs once per plan. Every tool call in the run shares one `run_id`.

Revise when the count is 0, when the count is greater than half the frozen household file (2,500 of 5,000), or when the tool returns a rejection. A rejection includes `forbidden_field`. The planner sees the previous predicate and the count or `error_class`. It does not see a gold band.

Allow one plan and two revisions, three attempts in all. A count from 1 through 2,500 on any attempt returns that draft audience and stops. The loop writes no file.

## 3. Stop when revision is exhausted

If the third attempt is still empty, still above 2,500, or still a rejection, the run returns nothing. A last attempt that names `age_years` writes no audience file. The log shows each rejection.

## 4. Campaign retrieval

Add `list_campaigns`. It reads `corpus/campaigns.json` and returns the four campaigns. It logs one record, with the same fields as the other tools. It does not read the gold file.

## 5. Grounded brief

The brief step runs only on an approved audience. The planner chooses a campaign id from `list_campaigns`. Code loads that campaign and copies `offer`, `channels`, and `constraint` into the shared brief schema, along with the approved audience and the campaign id.

A draft audience, a missing campaign id, or a brief that fails validation returns nothing. The offer text comes from the campaign record.

## 6. Write a file only after success

A small runner takes an objective string. A completed loop may write the draft audience. A miss, a rejection on the final attempt, or a schema failure writes no audience file and no brief file.

A brief file is written only when the audience is approved and the campaign id resolves. The runner does not approve an audience. The harness may set `approved`, then ask for the brief.

The harness may read `eval/gold.json` for the objective text and the size band. The graph still does not. A scripted planner covers a countable objective, an empty count, a count above 2,500, and `g07`. `g07` produces no audience file.

A short how-to says how to run the graph and where the log is written. The public README stays with M3.

## Done when

The loop revises on an empty count, a count above 2,500, and a forbidden field, then stops with no file when three attempts fail. An approved audience and a known campaign produce one brief copied from the campaign library. `eval/gold.json` stays unchanged. No one-shot path, no three-way score, no decision notes, and no UI.
